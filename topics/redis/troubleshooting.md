## Issue #1: Redis 테스트를 로컬 환경에 의존하지 않게 만들기

**발생일:** 2026-03-15
**심각도:** 🟡 Medium
**소요 시간:** 30분

### 📌 상황

Redis 실습은 외부 인프라 의존성이 크기 때문에, 로컬에 Redis가 실행 중이지 않으면 테스트가 깨질 수 있습니다.

### 🐛 증상

- 개발자마다 테스트 실행 조건이 달라짐
- `localhost:6379`에 Redis가 없으면 통합 테스트 실패

### 🔍 원인 분석

- 애플리케이션 실행은 Docker Compose로 해결할 수 있지만, 테스트는 더 독립적이어야 함
- Redis 의존 테스트를 로컬 서비스 상태에 기대면 재현성이 떨어짐

### ✅ 해결 방법

- Testcontainers로 Redis 컨테이너를 테스트 시점에 띄움
- `DynamicPropertySource`로 Redis host/port를 주입
- 각 테스트 전에 `FLUSHALL`로 상태 초기화

### 💭 회고

- Redis 주제는 실습형이라서 환경 재현성이 특히 중요합니다.
- 종합편일수록 테스트 독립성을 먼저 확보하는 편이 좋습니다.

## Issue #2: 분산 락은 단순 acquire보다 release 검증이 중요함

**발생일:** 2026-03-15
**심각도:** 🔴 High
**소요 시간:** 20분

### 📌 상황

Redis 락 예제를 구현할 때 가장 흔한 실수는 락 해제 시 소유권 검증 없이 키를 지우는 것입니다.

### 🐛 증상

- 다른 요청이 획득한 락을 잘못 해제할 수 있음
- 경쟁 상황에서 임계 구역 보호가 깨질 수 있음

### 🔍 원인 분석

- `SET NX PX`만 구현하고 `release`를 단순 `DEL`로 처리하면 안전하지 않음
- 최소한 저장된 토큰과 현재 토큰이 같은지 비교해야 함

### ✅ 해결 방법

- 락 획득 시 UUID 토큰 저장
- 해제 시 저장된 값과 현재 토큰 비교 후 삭제
- 실무에서는 Redisson 같은 라이브러리 사용 권장

### 💭 회고

- Redis 락은 “된다”보다 “안전하게 되는가”가 더 중요합니다.
